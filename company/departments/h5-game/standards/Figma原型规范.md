# Figma 原型规范

## 正式交付

- 策划必须在 Figma Design 中制作可编辑原生图层和 Prototype 连线。
- SVG、截图、本地 HTML 和生成图片只能作为临时素材，不能替代正式 Figma 文件。
- 每个项目默认使用一个 Figma Page，在其中分区排列主流程、交互说明、关卡布局、结算和反馈。
- 每个阶段只保留一个当前有效的正式评审区；项目必须记录文件 URL、Page、正式画板节点和确认状态。

## 版本迭代管理

- 适用范围：所有 H5 游戏项目的策划 Figma 原型，不限于单一项目或单一版本。
- 固定规则：既有版本列保持原位置、顺序和尺寸，不因实现、确认或状态变化移动；新版本始终在最右侧新增一列或版本卡。
- 已完成/已确定版本：列顶部统一使用第一列同款的绿色 `已实现功能` 标签，确保浏览时一眼可识别；不得再使用含义空泛的“版本迭代区”作为列标题。
- 待确认版本：必须使用明确的待确认状态标签和版本名称，不得用“版本迭代区”替代真实状态。
- 新版本操作：只在对应版本列内更新需求内容、版本标签和确认状态，不重排历史版本；实现状态变化时更新顶部状态标签，不搬动版本列。
- 解决的问题：避免版本来回移动造成预览顺序混乱、历史版本难以追溯，以及左右状态区与版本进度语义混用。
- 策划交付时必须检查：历史版本节点位置未变、最右侧新增版本列与上一列有明确间距、已完成/已确定列顶部为绿色 `已实现功能`、待确认列状态明确、当前正式评审区仍只有一个、截图无重叠或截断。
- 对现有 H5 项目的影响：已有项目按本规范逐步统一；只调整区域标签和后续新增版本的布局，不要求搬动历史版本或重做既有原型内容。

## 必备内容

- 初始界面与核心操作。
- 成功、受阻、胜利、失败和重新开始。
- 对玩法有影响的关键动画帧、空间规则和正反例。
- 可计算数值、交互热区、反馈持续时间和验收方法。

## 评论和反馈

- 评论图钉只负责定位，不能作为唯一需求记录。
- 每条意见同步为：`对象｜当前问题｜希望结果｜参考位置｜优先级`。
- 优先级为：`P0` 阻断、`P1` 明显影响体验、`P2` 一般优化。
- 处理状态为：`待处理 → 已理解 → 修改中 → 待复核 → 已完成`。
- 修改后必须说明改了什么、在哪里查看、按什么标准复核。

## 工具和安全

- 优先使用官方 Figma MCP 读取和修改原生图层，修改前确认账号具有编辑权限。
- 画布编辑与评论 API 是独立能力；项目可以保存自己的评论读取脚本。
- Figma Token 只保存在本机安全位置，不得进入项目文档、交接记录、日志或版本控制。

## 验证

- 修改后检查节点结构和截图，确认无截断、重叠、占位文字和错误状态。
- 正式画板名称、节点和本地策划版本必须相互对应。
- 如果工具不能编辑原生图层，必须停止并报告，不能用图片假装完成。
